# 1.1.1：强制通过原生插件打开画布

日期：2026-10-11。状态：实现、类型、构建、隔离数据回归与可移植包检查完成；本机已安装 1.1.1。当前聊天仍连接 1.1.0，新版原生 UI 待重新加载插件后观察。

## 需求与原因

用户要求画布必须通过 Codex Canvas 插件打开，不能自动切换浏览器。截图提示的是聊天附件不可用，不是画布无法渲染。

- 独立浏览器没有 MCP Apps 宿主桥，不能使用宿主上下文或消息接口。
- 原生面板是否启用聊天按钮仍取决于宿主实际声明，不能通过提示词伪造能力。
- 调整前的 Skill 会在旧连接或工具缺失时自动使用 CLI 浏览器回退；MCP 进程也会返回浏览器 URL，容易把原生打开要求降级成浏览器交付。

## 实现

- Canvas Skill 将原生交付设为硬要求：使用 `canvas_open_file`、`canvas_open` 或 `canvas_publish`，缺少工具或遇到旧连接时说明原因并停止打开步骤，保留源码。
- MCP 初始化指令和工具描述重复声明原生打开要求；工具结果包含 `presentation.mode: native-mcp-app` 和 `browserFallback: false`，不提供浏览器 `previewUrl`。
- stdio 插件进程不启动 HTTP 监听，原生 App 继续通过显式服务端会话和 MCP 工具调用工作。历史服务身份和资源 URI 保留。
- CLI `open` 必须显式带 `--browser`；HTTP 服务必须显式带 `--serve`。这些入口只用于用户明确需要的独立浏览器模式，不能作为原生失败时的自动回退。
- 选区提示区分独立浏览器与原生宿主能力缺失；缺少能力时保留复制选区入口。
- 中英文 README、快速开始和示例说明包含可直接复制的强制原生提示词。

## 证据与边界

- 本次先通过已安装的 1.1.0 `canvas_open` 重新打开同一张架构图。MCP Apps 面板实际出现，DOM 显示 `mode=panel`、`MCP App 已连接`，添加上下文和发送按钮均未禁用。没有代用户添加附件或发送消息。
- 这证明当前宿主提供原生入口和已声明聊天能力，不代表发送调用已经执行或新版安装后的 UI 已观察。
- 不修改用户源码、删除状态或交互记录，不启动新的浏览器预览。
- 原生打开改动先通过类型/构建与 Skill 静态校验。随后用户明确要求修复 CI，授权运行检查；`pnpm check` 的 22 项测试全部通过，包括原生工具无浏览器链接、服务端打开指令、CLI 拒绝隐式浏览器打开和历史资源兼容。
- 可移植 1.1.1 从锁文件安装依赖、独立 stdio 启动和真实 TSX 编译均通过。CLI 安装记录确认本机版本 1.1.1；当前聊天的 `canvas_list` 仍返回 1.1.0，因此未将旧面板作为新版 UI 证据，也未自动切换浏览器。
